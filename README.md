# Граф денег

Локальный инструмент для AML-аналитика: строит граф внутрибанковских переводов, назначает объяснимые структурные роли, ранжирует клиентов для проверки и показывает направленные связи. Роли и приоритеты являются гипотезами для аналитика, а не утверждениями о виновности.

## Запуск

Нужен Python 3.12. Из корня репозитория:

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python starter.py --data data --out out
.venv/bin/streamlit run app.py
```

На Windows используйте `.venv\Scripts\python` и `.venv\Scripts\streamlit`. CLI-команда делает полный пересчёт из трёх сырых parquet и создаёт `out/nodes_roles.csv`, `out/clusters.csv`, `out/top_nodes.csv` и `out/manifest.json`; UI и API-ключ для неё не нужны. Приложение повторяет тот же расчёт по кнопке «Рассчитать». Можно выбрать вложенный в репозиторий набор или загрузить свои `nodes.parquet`, `edges.parquet`, `transactions.parquet` с той же схемой. Для загруженных файлов расчёт идёт во временной папке: он не перезаписывает эталонные `out/`, а три CSV доступны для скачивания в интерфейсе. При смене файла прежний результат скрывается до нового расчёта. На предоставленном наборе вход содержит 2248 узлов, 3119 пар переводов, 4840 транзакций.

Основное демо: рассчитать → открыть топ приоритетов → найти произвольный gid → посмотреть роль, обоснование, входящие и исходящие связи → скачать три CSV. Период над результатом берётся из дат загруженных транзакций. Для тестов: `.venv/bin/python -m pytest -q`.

В топ-листе можно выбрать строку, чтобы сразу открыть карточку этого клиента. Карточка также показывает активность по дням и число дней, когда в наблюдаемом наборе были одновременно входящие и исходящие переводы. Это сигнал для проверки, а не доказательство сквозного транзита: у транзакций есть дата, но нет времени внутри дня. Временные сигналы не меняют обязательные роли и три CSV.

## Роли и приоритет

Все пороги лежат в `config.json`. Проверяются по порядку; первая подходящая роль становится основной:

| Роль | Правило |
|---|---|
| coordinator | Достижим от ≥3 seed, есть вход и выход, процентиль направленного посредничества ≥0,90 и соседство с ≥2 другими кластерами |
| distributor | ≥10 разных получателей |
| transit | Не seed; вход и выход >0; наблюдаемый выход/вход в [0,8; 1,2] |
| consolidator | ≥3 разных плательщиков и положительная входящая сумма |
| terminal | Вход >0, выход=0, depth<4, не seed |
| peripheral | Другие правила не сработали или недостаточно наблюдений |

Численные признаки: число разных контрагентов и транзакций, суммы, взвешенный PageRank, достижимость от seed, приближённое направленное betweenness (до 128 исходных узлов), соседство кластеров. Сумму нельзя использовать как расстояние для betweenness; он считается без веса. `role_score` — сила выполнения правила, а не вероятность истины: 0,5 + до 0,4 за профильный признак, 0,2 для peripheral, 0 для изолятов; на обрезанном колене максимум 0,6. Точные формулы реализованы в `analysis.py`.

`priority_score` — сумма процентильных факторов: 0,30 × достижимость от seed + 0,25 × входящая сумма + 0,20 × максимум входящей/исходящей степени + 0,15 × посредничество + 0,10 × PageRank. Для нулевого признака процентиль равен 0. Изоляту приоритет 0. В `top_nodes.csv` приведены основания, сортировка при ничьей — по gid. Это эвристика очередности проверки, не риск преступления.

Кластеры строятся Louvain с фиксированным seed на неориентированной проекции; суммы встречных переводов складываются. Направленный граф сохраняется для потоков и ролей. Каждый изолят получает отдельный кластер. Номера кластеров стабилизированы по минимальному gid. `sum_kzt_internal` суммирует только направленные рёбра внутри кластера, каждое один раз.

## Справка аналитика и AI

Карточка всегда содержит правиловую справку с основаниями, дневным совпадением потоков, ограничениями и предлагаемым следующим запросом данных. Если указан `OPENAI_API_KEY`, появляется отдельная кнопка AI-справки. Она передаёт модели только признаки выбранного синтетического gid и до 10 связанных gid, запрашивает структурированный ответ и проверяет ссылки на данные; использованные признаки показаны в карточке. Модель не меняет роли, приоритет или CSV. При таймауте/ошибке используется явно обозначенная правиловая справка. Модель задаётся через `OPENAI_MODEL` (по умолчанию `gpt-4o-mini`). Ключ можно задать переменной окружения или в файле `.env` в корне репозитория по образцу `.env.example`; переменная окружения имеет приоритет. Вписывайте ключ только в `.env`: он исключён из Git, а `.env.example` отслеживается. Сценарии успеха и таймаута проверены с имитацией API; один живой вызов для синтетического gid также проверен в интерфейсе. Использован формат Structured Outputs из [официальной документации OpenAI](https://developers.openai.com/api/docs/guides/structured-outputs).

## Ограничения данных

- Исходный набор охватывает только исходящие переводы от 81 seed по четырём коленам, внутри одного банка, за июль 2026 года, с порогом 5000 KZT. Входящие извне выборки и меньшие переводы не видны.
- Все 444 узла depth=4 без исходящих находятся на границе обхода. Они не объявляются terminal только из-за отсутствия видимых исходящих.
- Входящие seed могут быть занижены. Отношение выхода к входу у seed не используется для transit.
- 19 изолятов входят в экспорт и поиск. С рёбрами видны 16 слабосвязных компонент, с изолятами — 35.
- У данных нет истинных меток ролей, личных атрибутов и остатков. `role_score` нельзя интерпретировать как подтверждённую точность; нет оценки accuracy. Дневная гранулярность транзакций не доказывает последовательность внутри суток.
- Схема отображает ограниченное окружение выбранного gid ради читаемости. Расчёт и CSV используют все узлы.

При росте до ~1 млн узлов потребуются колонночная обработка parquet, специализированный графовый движок, приближённые метрики, хранение результатов и выдача подграфов по запросу. Данная реализация на таком масштабе не проверялась.
